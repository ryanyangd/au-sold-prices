# Deploying to Azure with GitHub Actions (dev and prod)

Everything runs in the cloud after deployment: the web app and API on Azure Container Apps, the
database on PostgreSQL Flexible Server, the daily download on an Azure Function, and the data
pipeline on Databricks. You approve each production release in GitHub.

```text
pull request -> CI checks -> merge to main
   -> DEV:  plan -> (auto) -> infra -> images -> release -> smoke test -> data refresh
   -> PROD: plan -> YOUR APPROVAL -> infra -> images -> release -> smoke test -> data refresh
```

| | dev | prod |
|---|---|---|
| Resource group | `rg-ausold-dev-aue` | `rg-ausold-prod-aue` |
| Sign-in | dev login until Entra is configured | Entra External ID required (deploy refuses without it) |
| Postgres | Burstable `Standard_B2s` | General Purpose `Standard_D2ds_v5`, 14-day backups |
| Web/API replicas | 1+ | 2+ |
| Budget alert | A$600 / month | A$1,400 / month |
| GitHub approval | none | you must approve (`prod-approval`) |

They can live in one Azure subscription (names differ by environment) or in two; run the Azure
bootstrap once per subscription.

## 1. Prerequisites

- Azure subscription(s) where you can assign roles (Owner, or Contributor + User Access Administrator).
- `az` (Azure CLI), `gh` (GitHub CLI, logged in with `gh auth login`), `openssl`.
- A GitHub repo plan that supports **required reviewers on environments**: public repos, or
  private repos on GitHub Pro/Team/Enterprise. Without it `prod` cannot be gated; see
  [Without environment reviewers](#without-environment-reviewers).
- Databricks needs the identity that deploys to be allowed to create a Unity Catalog storage
  credential (see [Databricks notes](#databricks-notes)).

## 2. One-time setup (before the first merge)

Do this before merging the code to `main`, because a merge to `main` starts a dev deployment.

### 2.1 Let GitHub deploy to Azure without passwords (OIDC)

```sh
az login
az account set --subscription <dev-subscription-id>
scripts/azure-bootstrap.sh dev            # prints export lines at the end

az account set --subscription <prod-subscription-id>   # same one is fine
scripts/azure-bootstrap.sh prod
```

Each run creates a service principal `sp-github-ausold-<env>`, trusts GitHub's tokens for the
repo's `<env>` environment, and grants Contributor plus User Access Administrator on the
subscription. No secret is created.

### 2.2 Create the GitHub environments, variables and secrets

Copy the `export` lines printed by the bootstrap, then:

```sh
export ALERT_EMAIL=you@example.com
scripts/github-setup.sh dev
# repeat the bootstrap exports for prod, then:
scripts/github-setup.sh prod
```

This creates the environments `dev`, `dev-approval`, `prod` and `prod-approval` (you are the
required reviewer on `prod-approval`; all are limited to the `main` branch), the issue labels the
workflows use, the variables below and a random Postgres admin password (stored only as a GitHub
secret and in Azure Key Vault).

| Name | Kind | Needed | Meaning |
|---|---|---|---|
| `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID` | variable | always | Azure login |
| `ALERT_EMAIL` | variable | always | Budget and failure alerts |
| `DEPLOYER_OBJECT_ID`, `ADMIN_OBJECT_ID` | variable | recommended | Roles for CI and for you (Key Vault, lake upload) |
| `PG_ADMIN_PASSWORD` | secret | always | Generated by the script |
| `ENTRA_TENANT_ID`, `ENTRA_TENANT_SUBDOMAIN`, `ENTRA_API_AUDIENCE` | variable | prod | API token validation |
| `NEXT_PUBLIC_ENTRA_CLIENT_ID`, `NEXT_PUBLIC_ENTRA_AUTHORITY`, `NEXT_PUBLIC_ENTRA_API_SCOPE` | variable | prod | Web sign-in (compiled into the web build, so public) |
| `STRIPE_PRICE_MONTHLY`, `STRIPE_PRICE_ANNUAL` | variable | for payments | Stripe price IDs |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | secret | for payments | Stripe keys (use test mode until data licensing is settled) |

To add or change one later: `gh variable set NAME --env prod --body value` or
`gh secret set NAME --env prod`, then re-run the deployment.

### 2.3 Sign-in and payments (manual, can wait for dev)

- **Entra External ID** (prod needs it): create an external tenant, register an API app (expose
  an `access_as_user` scope) and a single-page app (redirect URI = the web URL printed by the
  first deployment), add Google, Microsoft and Facebook as identity providers on a sign-up/sign-in
  user flow. Set the `ENTRA_*` and `NEXT_PUBLIC_ENTRA_*` values above and redeploy.
- **Stripe**: create a Pro product with monthly and annual prices; add a webhook endpoint
  `<API URL>/webhooks/stripe` for `customer.subscription.created`, `.updated` and `.deleted`.
  The API URL appears in the deployment summary. Set the Stripe variables and secrets, redeploy.

### 2.4 Put the code on GitHub

Everything in this repo is currently uncommitted. Review what will be committed (nothing from
`data/` or `docs-private/` should appear):

```sh
git checkout -b feature/cloud-deploy
git status
git add -A
git commit -m "Add data pipeline, API, web app, Azure infra and deployment workflows"
git push -u origin feature/cloud-deploy
gh pr create --fill
```

CI runs on the pull request (Python on 3.10 and 3.12 with Postgres, web, Bicep). Fix anything it
reports, then merge.

## 3. First deployment

Merging to `main` starts **Deploy** automatically (dev only, until you enable prod: run
`gh variable set PROD_ENABLED --body true` once Entra sign-in is configured for prod). You can also
start it by hand:

```sh
gh workflow run deploy.yml -f target=dev           # dev only
gh workflow run deploy.yml -f target=dev-then-prod # dev, then prod after your approval
gh run watch
```

What each stage does (per environment):

1. **Plan**: runs an Azure what-if and shows the list of changes in the run summary.
2. **Approve**: `dev` continues by itself. For `prod` the run stops and GitHub emails you; open
   the run, review the plan, and click **Review deployments > Approve and deploy**.
3. **Deploy**: registers resource providers, deploys the Bicep, builds the API and web images in
   Azure Container Registry (no Docker needed on the runner), deploys them, publishes the ingest
   function, then runs the smoke test (API health, database, web page, search).
4. **Data refresh**: see below.

Expect 20 to 30 minutes the first time (Databricks, Postgres and Container Apps are slow to
create), and 10 to 15 minutes afterwards. The run summary lists the web, API and Stripe webhook
URLs.

## 4. Data upload and the cloud pipeline

The **Data refresh** workflow (`data-refresh.yml`) runs after every deployment and can be run by
hand:

```text
Azure Function (daily ~05:00 Sydney)  -> raw/nsw_psi/<date>/{archive.zip,data.csv,_manifest.json}
Databricks job (daily 07:00 Sydney)  -> bronze -> silver -> gold -> Postgres `serving` schema
API / web                             -> read the new data immediately (schema swap, no downtime)
```

During a deployment the workflow:

1. Triggers the ingest function once and waits until a completed folder (with its manifest)
   exists in `raw/nsw_psi/`.
2. Prepares Unity Catalog (storage credential, external locations, catalog `ausold`) and a
   Databricks secret holding the database URL, then deploys and runs the bundle in
   `pipelines/databricks`.
3. Checks that the API search returns properties.

### If the source download is blocked or stale

The public source can lag or block automated downloads. Upload a CSV yourself; it goes straight
to the lake and never into git:

```sh
az login
scripts/upload-csv.sh dev data/nsw-property-sales-data-updated20260914.csv
gh workflow run data-refresh.yml -f environment=dev -f run_ingest=false
```

(`ADMIN_OBJECT_ID` must be set so you have the lake upload role.)

### Check the data landed

```sh
az storage blob list --auth-mode login --account-name <lake> -c raw --prefix nsw_psi/ -o table
curl "<API URL>/search/addresses?q=george%20st"
```

In Databricks, open the workspace URL (deployment outputs) and check job `nsw-sales-pipeline-<env>`
and the tables in catalog `ausold` (`bronze`, `silver`, `gold`). Failed runs raise alerts to
`ALERT_EMAIL` and open a GitHub issue.

### Databricks notes

- The bootstrap uses the identity that created the workspace (the CI service principal). If the
  workspace has no Unity Catalog metastore, or that identity cannot create storage credentials,
  `scripts/ci/databricks-run.sh` fails with a clear message. Fix by attaching a metastore in the
  Databricks account console and making the service principal a metastore admin, or create the
  credential, external locations (`raw`, `lakehouse`) and catalog `ausold` yourself (see
  `infra/README.md`), then re-run the **Data refresh** workflow.
- This Databricks part could not be exercised outside Azure while it was written. Treat the first
  `dev` run as its real test and read the Databricks job log if it fails.
- Each source file is a full snapshot and silver reads only the newest one. Older bronze versions
  can be vacuumed later to save storage.

## 5. Verify everything runs in the cloud

```sh
# Apps
az containerapp list -g rg-ausold-dev-aue -o table
curl -fsS <API URL>/health/ready
# Scheduled work
az functionapp function show -g rg-ausold-dev-aue -n <function app> --function-name ingest_nsw_sales
# Costs and alerts
az consumption budget list -o table
```

Application Insights (`appi-ausold-<env>`) holds the function and API logs; the alert rule
`alert-ausold-<env>-ingest-problem` emails you when the ingest fails or the data is stale (older
than 14 days).

## 6. Day-to-day releases

Normal flow: change code in a branch, open a PR, wait for CI, merge. Merging deploys `dev`
automatically, then waits for your approval to deploy `prod`. Test on the dev URL before approving.

- **Redeploy / retry:** `gh workflow run deploy.yml -f target=dev` (or `prod`).
- **Roll back:** revert the merge on `main` (`gh pr create` from a revert branch); the revert
  deploys like any change. For an urgent rollback run the Deploy workflow for `prod` on the
  reverted commit.
- **Rotate the Postgres password:** `gh secret set PG_ADMIN_PASSWORD --env <env>` then redeploy.
- **Logs:** GitHub Actions run logs for deployments; `az containerapp logs show -g <rg> -n <app>`.

### Known limits of this first version

- Postgres accepts connections from Azure services (TLS only), and the API uses the admin login.
  Add private networking and a least-privilege database role before real customers or payments.
- No custom domain, CDN or WAF yet.
- Commercial use of the data is not licensed. Keep Stripe in test mode and sign-ups closed until
  the licensing work is done.

### Without environment reviewers

If your plan does not allow required reviewers, `scripts/github-setup.sh prod` reports that it
could not create `prod-approval`. Options: make the repo public (no secrets are in it), upgrade
the plan, or change `prod` to deploy only by manual `workflow_dispatch` and protect `main` with a
ruleset so only you can run it.

## 7. Automating pull requests and bug fixes with GitHub Copilot

You stay the approver: Copilot proposes changes, CI checks them, you review and approve, and the
pipeline deploys. Nothing reaches `prod` without your click.

### 7.1 One-time setup

1. **Turn on Copilot coding agent** for the repo (Settings > Copilot > Coding agent; needs a Copilot
   plan that includes it, and an organisation admin may have to allow it).
2. **Protect `main`** (Settings > Rules > Rulesets > New branch ruleset, target `main`):
   require a pull request, require approval from code owners (`.github/CODEOWNERS` makes you the
   owner), require status checks `test (3.10)`, `test (3.12)`, `web` and `bicep`, block force pushes.
3. **Automatic Copilot code review**: in the same ruleset enable *Automatically request Copilot
   code review* so every PR gets a first review.
4. Commit the files that guide the agent (already in the repo): `.github/copilot-instructions.md`
   (conventions and commands), `.github/workflows/copilot-setup-steps.yml` (its build
   environment), the bug-report issue template and the PR template.
5. Dependabot (`.github/dependabot.yml`) opens weekly dependency update PRs through the same flow.

### 7.2 Fixing a bug with Copilot, step by step

1. **File the bug.** Issues > New > *Bug report* (area, environment, steps, logs). Failed deployments
   and failed data refreshes open an issue for you automatically (labels `bug`,
   `deploy-failure`/`data-pipeline`).
2. **Assign it to Copilot.** On the issue, set *Assignees* to **Copilot** (or
   `gh issue edit <n> --add-assignee "@copilot"`). Copilot reads the issue and the repo
   instructions, works in the cloud, and opens a draft PR on a `copilot/...` branch.
3. **Let CI run.** Workflows on Copilot PRs wait for you: open the PR and click **Approve and run
   workflows**. Check that `test`, `web` and `bicep` pass.
4. **Review.** Read the diff and Copilot's summary, confirm a regression test was added, and use
   *Request changes* or comments such as `@copilot please also handle empty suburbs` to iterate.
   Copilot code review adds its own comments. You approve as code owner.
5. **Merge.** Mark the PR ready and merge. This triggers **Deploy**: `dev` goes out automatically.
6. **Verify on dev**, then open the run and approve `prod` (**Review deployments**).
7. The issue closes with the PR (`Fixes #n`).

### 7.3 Fixing a failed deployment

The Deploy workflow opens an issue titled *Deployment failed: <sha>* with a link to the run.
Assign it to Copilot as above. It reads the logs, proposes a fix PR, and you review and merge it.
For infrastructure or workflow changes, review more closely: the repository instructions tell
Copilot not to touch production settings, but you remain the gate.

### 7.4 Guardrails you keep

- Copilot cannot approve its own PR or the production environment; only you can.
- Copilot works with no access to your Azure subscription or environment secrets.
- Branch protection plus CODEOWNERS means nothing merges without your review.
- The `prod-approval` environment requires your click for every production deployment.
- Local alternative: in VS Code use Copilot Chat in agent mode on a branch, run
  `scripts/dev-stack.sh check`, then open a PR through the same pipeline.
